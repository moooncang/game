# 회사 시스템 설계

AI 사원 두 명이 한 회사 직원처럼 일하고, 사장님이 그 과정을 **도트 감성 회사 홈페이지**에서 지켜보며 서류로 보고받는 시스템의 설계 문서입니다.

## 1. 핵심 아이디어: GitHub 저장소 = 회사

별도 서버나 DB 없이 **GitHub 저장소 하나가 사무실, 업무 시스템, DB 역할을 모두** 합니다.
두 AI 모두 GitHub에 접근할 수 있으므로 별도 MCP 서버를 운영할 필요가 없습니다.

| 회사 개념 | GitHub에서 | 누가 |
|---|---|---|
| 업무 지시서 | **Issue** (템플릿: 업무 지시서) | 사장님 |
| 담당자 지정 | Issue 라벨 `담당:claude` / `담당:gpt` | 사장님 |
| 출근·상태 보고 | Issue **댓글** (`office:status` 양식) | 사원 |
| 서류(업무 보고서) 제출 | Issue **댓글** (`office:report` 양식) | 사원 |
| 서류 제출 단위 | **큰 갈래별로 여러 장** (문서 번호 `이슈번호-순번`) | 사원 |
| 피드백·결재 | Issue 댓글 `/피드백 번호 내용`, `/승인 번호`, `/반려 번호 사유` | 사장님 |
| 출근 (업무 시작) | **출근 버튼** = GitHub Actions 수동 실행 | 사장님 |
| 결과물 | **PR** (`Closes #N`) | gpt (실무) |
| 결과물 검수 | PR 리뷰 | claude |
| 최종 반영 | PR 머지 | 사장님 |
| 회사 홈페이지 | **GitHub Pages** | GPT 제작 |

> 상태와 서류를 **파일 커밋이 아닌 Issue 댓글로** 하는 이유:
> 커밋은 브랜치 → PR → 머지를 거쳐야 홈페이지에 보이지만, 댓글은 즉시 기록됩니다.
> 두 사원이 같은 파일을 고쳐 충돌이 날 일도 없습니다.

## 2. 전체 흐름

### 2-1. 업무 순환
```
 👔 사장님          🤖 GPT (실무)            🤖 Claude (검수·아이디어·시스템)
     │
     ├─ 업무 Issue 생성 (담당 라벨)
     ├─ [출근] 버튼 ─────▶ 깨어남
     │                    ├─ 작업 → PR 제출
     │                    └─ 갈래별 서류 제출 (2-1, 2-2, 2-3…)
     │                         │  (전원 출근이면 이어서)
     │                         └──────────────────▶ 깨어남
     │                                               ├─ GPT PR 검수 (리뷰)
     │                                               └─ 검수결과·기획안 서류
     ├─ 서류마다 /피드백 · /승인 · /반려 쌓아 두기   (사원은 깨어나지 않음)
     ├─ [출근] 버튼 ─────▶ 쌓인 피드백 전부 처리 → 답변 서류 (`답변: 2-2`)
     └─ PR 머지
```

### 2-2. 데이터 흐름
```
 Issue · 댓글 · PR ──(이벤트)──▶ GitHub Actions: 피드 생성기 ──▶ feed.json
                                                              │
                                     GitHub Pages 배포 (1~2분) ▼
                                              🏢 도트 회사 홈페이지
                                   (캐릭터 행동 · 서류함 · 피드백 상태 · 출근 버튼)
```

## 3. 구성 요소

### 3-1. 업무 데이터 규격 (`office/`) — Claude 관리
- 상태 보고 댓글, 업무 보고서 댓글, 결재 댓글의 양식.
- 홈페이지가 읽는 `feed.json`의 구조.
- 자세한 규격: [`office/README.md`](../office/README.md)

### 3-2. 피드 생성기 (GitHub Actions) — GPT 제작
- 트리거: `issues`, `issue_comment`, `pull_request` 이벤트 + 혹시 모를 누락 대비 주기 실행(예: 30분마다).
- 하는 일: GitHub API(Actions 기본 `GITHUB_TOKEN`)로 Issue·댓글·PR을 읽어 `feed.json` 생성 → 사이트와 함께 Pages에 배포.
- 장점: 방문자 브라우저가 GitHub API를 직접 부르지 않아 **API 호출 제한(비로그인 시간당 60회)에 걸리지 않습니다.**

### 3-3. 도트 회사 홈페이지 (`site/`) — GPT 제작
- 도트 사무실 맵, 사원 캐릭터 2명, 사장실 서류함.
- `feed.json`을 주기적으로 다시 읽어 캐릭터 행동과 서류함을 갱신.
- 상세 요구사항: [`docs/handover/website.md`](handover/website.md)

### 3-4. 출근 버튼 (GitHub Actions 수동 실행) — GPT 제작
- AI는 **스스로 깨어나지 않습니다.** 사장님이 피드백을 다 남긴 뒤 출근 버튼을 누르면 그때 실행됩니다.
- 버튼: `[GPT 출근]`, `[Claude 출근]`, `[전원 출근]` (기본 순서대로: GPT → Claude 검수, 옵션으로 동시)
- 구현: `workflow_dispatch` 워크플로. 홈페이지 버튼은 GitHub의 워크플로 실행 화면을 열어 주고, 사장님이 **Run workflow**를 누릅니다. 저장소 주인만 실행할 수 있어 외부인이 사원을 깨울 수 없습니다.
- 실행 엔진 후보: Claude는 Claude Code GitHub Actions, GPT는 Codex를 GitHub Actions에서 실행하는 OpenAI 공식 액션. 구현할 때 지원 범위를 확인합니다.
- 한 사원은 동시에 한 번만 실행 (`concurrency` 그룹 = 사원 ID).
- API 키(또는 Claude 구독 토큰)는 반드시 GitHub **Secrets**에 저장합니다. (공개 저장소이므로 파일에 쓰면 안 됨)
- API 사용료가 발생하므로 한 번 출근에 쓸 수 있는 최대 작업 시간·횟수를 정해 둡니다.
- 꼬임 방지 규칙: [`office/README.md` §4-3](../office/README.md#4-3-동시-작업-규칙-꼬임-방지)

## 4. 알려진 한계

- **실시간이 아닙니다.** 댓글 → Actions 실행 → Pages 배포까지 약 1~2분 지연됩니다.
- **홈페이지는 읽기 전용**입니다. 지시·피드백·결재·출근은 GitHub 화면에서 합니다. 홈페이지 버튼은 해당 GitHub 화면을 열어 주는 역할만 합니다. (나중에 중계 서버를 붙이면 홈페이지에서 바로 쓰도록 바꿀 수 있습니다)
- **공개 사이트입니다.** 홈페이지와 저장소 내용은 누구나 볼 수 있습니다. 보고서에 민감한 내용을 쓰지 않습니다.
- 두 AI와 사장님이 모두 같은 GitHub 계정(`moooncang`)으로 글을 씁니다. 그래서 작성자는 계정 이름이 아니라 **GitHub가 기록하는 앱 정보(`performed_via_github_app`)** 로 구분합니다. 이 값은 AI가 조작할 수 없습니다. 자세한 규칙: [`office/README.md` §6 신원 확인](../office/README.md#6-신원-확인-누가-쓴-댓글인가)
- 유니티 에디터 실행·빌드는 사장님 PC에서만 가능합니다.
