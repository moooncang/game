# 회사 시스템 설계

AI 사원 두 명이 한 회사 직원처럼 일하고, 사장님이 그 과정을 **도트 감성 회사 홈페이지**에서 지켜보며 서류로 보고받는 시스템의 설계 문서입니다.

## 1. 핵심 아이디어: GitHub 저장소 = 회사

별도 서버나 DB 없이 **GitHub 저장소 하나가 사무실, 업무 시스템, DB 역할을 모두** 합니다.
두 AI 모두 GitHub에 접근할 수 있으므로 별도 MCP 서버를 운영할 필요가 없습니다.

| 회사 개념 | GitHub에서 | 누가 |
|---|---|---|
| 업무 지시서 | **Issue** (템플릿: 업무 지시서) | 사장님 |
| 담당자 지정 | Issue 라벨 `담당:claude` / `담당:gpt` | 사장님 |
| 출근·상태 보고 | Issue **댓글** (`office:status` 양식) | 사원 |
| 서류(업무 보고서) 제출 | Issue **댓글** (`office:report` 양식) | 사원 |
| 결재 | Issue 댓글 `/승인`, `/반려 사유` | 사장님 |
| 결과물 | **PR** (`Closes #N`) | 사원 |
| 결과물 검토 | PR 리뷰 (교차 리뷰) | 사원 |
| 최종 반영 | PR 머지 | 사장님 |
| 회사 홈페이지 | **GitHub Pages** | GPT 제작 |

> 상태와 서류를 **파일 커밋이 아닌 Issue 댓글로** 하는 이유:
> 커밋은 브랜치 → PR → 머지를 거쳐야 홈페이지에 보이지만, 댓글은 즉시 기록됩니다.
> 두 사원이 같은 파일을 고쳐 충돌이 날 일도 없습니다.

## 2. 전체 흐름

```
  👔 사장님 ──① Issue 생성(업무 지시) ──┐
                                       ▼
                             ┌────────────────────┐
  🤖 Claude ──② 상태 댓글───▶│                    │
  🤖 GPT    ──③ 보고서 댓글─▶│   GitHub 저장소     │
            ──④ PR 제출────▶│ (Issue · PR · 코드) │
  👔 사장님 ──⑤ /승인 댓글──▶│                    │
                             └─────────┬──────────┘
                                       │ ⑥ 이벤트 발생 시 GitHub Actions 실행
                                       ▼
                             ┌────────────────────┐
                             │ 피드 생성 스크립트   │  Issue·댓글·PR을 읽어서
                             │ → feed.json        │  홈페이지용 데이터로 정리
                             └─────────┬──────────┘
                                       │ ⑦ GitHub Pages 배포 (약 1~2분)
                                       ▼
                             ┌────────────────────┐
                             │ 🏢 도트 회사 홈페이지 │  캐릭터가 움직이고
                             │                    │  서류함에 보고서 도착
                             └────────────────────┘
```

## 3. 구성 요소

### 3-1. 업무 데이터 규격 (`office/`) — Claude 관리
- 상태 보고 댓글, 업무 보고서 댓글, 결재 댓글의 양식.
- 홈페이지가 읽는 `feed.json`의 구조.
- 자세한 규격: [`office/README.md`](../office/README.md)

### 3-2. 피드 생성기 (GitHub Actions) — GPT 제작
- 트리거: `issues`, `issue_comment`, `pull_request` 이벤트 + 혹시 모를 누락 대비 주기 실행(예: 30분마다).
- 하는 일: GitHub API(Actions 기본 `GITHUB_TOKEN`)로 Issue·댓글·PR을 읽어 `feed.json` 생성 → 사이트와 함께 Pages에 배포.
- 장점: 방문자 브라우저가 GitHub API를 직접 부르지 않아 **API 호출 제한(비로그인 시간당 60회)에 걸리지 않습니다.**

### 3-3. 도트 회사 홈페이지 (`site/`) — GPT 제작
- 도트 사무실 맵, 사원 캐릭터 2명, 사장실 서류함.
- `feed.json`을 주기적으로 다시 읽어 캐릭터 행동과 서류함을 갱신.
- 상세 요구사항: [`docs/handover/website.md`](handover/website.md)

### 3-4. 자동 출근 장치 (예정, 미착수)
- AI는 업무가 생겨도 **스스로 깨어나지 않습니다.** 지금은 사장님이 각 AI에게 "업무 확인해"라고 말해야 합니다.
- 자동화하려면: 새 Issue에 담당 라벨이 붙으면 해당 AI를 실행하는 장치가 필요합니다.
  - 후보: GitHub Actions에서 Claude Code / Codex를 실행하는 공식 액션, 또는 사장님 PC의 스케줄러.
- API 사용료가 발생하므로 **하루 업무량 한도**를 함께 설계해야 합니다.
- 비밀 키는 반드시 GitHub **Secrets**에 저장합니다. (공개 저장소이므로 파일에 쓰면 안 됨)

## 4. 알려진 한계

- **실시간이 아닙니다.** 댓글 → Actions 실행 → Pages 배포까지 약 1~2분 지연됩니다.
- **홈페이지는 읽기 전용**입니다. 지시·결재는 GitHub 화면에서 합니다. 홈페이지 버튼은 해당 GitHub 화면을 열어 주는 역할만 합니다.
- **공개 사이트입니다.** 홈페이지와 저장소 내용은 누구나 볼 수 있습니다. 보고서에 민감한 내용을 쓰지 않습니다.
- 사원 구분은 GitHub 계정이 아니라 **댓글 양식 안의 `사원:` 값**으로 합니다. (두 AI가 같은 계정·앱 이름으로 댓글을 달 수 있기 때문)
- 유니티 에디터 실행·빌드는 사장님 PC에서만 가능합니다.
