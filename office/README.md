# 업무 데이터 규격 (office) — v2

AI 사원의 **상태 보고**, **서류(업무 보고서)**, 사장님의 **피드백·결재**, 그리고 **출근(업무 시작)** 을 남기는 양식입니다.
회사 홈페이지는 이 양식을 해석해서 캐릭터를 움직이고 서류함을 채웁니다. **양식을 정확히 지켜 주세요.**

모든 보고·피드백·결재는 **해당 업무 Issue의 댓글**로 남깁니다.
댓글 첫 줄의 HTML 주석 표식(`<!-- office:... -->`)으로 종류를 구분합니다. 이 주석은 GitHub 화면에는 보이지 않습니다.

## 0. 한눈에 보는 업무 순환

```
① 사원이 일을 끝내면 → 큰 갈래별로 서류를 나눠 제출        (§2)
     [2-1] 화면 구성   [2-2] 색감   [2-3] 연출   [2-4] 테스트
② 사장님이 서류마다 피드백·결재를 남겨 둠 (사원은 아직 안 깨어남) (§3)
     /피드백 2-2 바닥 색이 너무 어두워요
     /승인 2-1
③ 사장님이 출근 버튼을 누름: [GPT 출근] [Claude 출근] [전원 출근]  (§4)
④ 깨어난 사원이 자기 서류에 쌓인 미처리 피드백을 전부 가져가 처리
⑤ 처리 결과를 다시 갈래별 서류로 제출 (`답변: 2-2`로 원래 서류와 연결)
```

## 1. 상태 보고 (`office:status`)

출근(작업 시작), 작업 종류가 바뀔 때, 퇴근(작업 종료) 때 남깁니다.

```markdown
<!-- office:status -->
사원: gpt
상태: coding
메시지: 2-2 피드백 반영 중 (바닥 색)
```

| 항목 | 필수 | 값 |
|---|---|---|
| `사원` | ✅ | `claude` 또는 `gpt` |
| `상태` | ✅ | 아래 상태 코드 중 하나 |
| `메시지` | ✅ | 한 줄 설명 (홈페이지 말풍선에 표시, 40자 이내 권장) |

### 상태 코드 → 홈페이지 행동

| 코드 | 의미 | 캐릭터 행동 (권장) |
|---|---|---|
| `offline` | 퇴근 | 자리에 없음 (책상 비어 있음) |
| `idle` | 대기 | 자리에 앉아 쉬거나 사무실을 어슬렁거림 |
| `coding` | 코딩 중 | 자기 책상에서 타이핑 |
| `designing` | 도트 아트·디자인 중 | 책상에서 그림 그리기(펜 태블릿) |
| `writing` | 기획·문서·대사 작성 중 | 책상에서 종이에 쓰기 |
| `reviewing` | 동료 결과물 검수 중 | 동료 책상으로 걸어가서 모니터 보기 |
| `meeting` | 회의·질문 대기 | 회의 테이블로 이동 |
| `blocked` | 막힘, 사장님 도움 필요 | 머리 위에 `!` 표시, 제자리에서 고민 |

> 상태 코드를 새로 추가할 때는 이 표를 먼저 고칩니다. 홈페이지는 모르는 상태 코드를 받으면 `idle`로 처리해야 합니다.

## 2. 서류 (`office:report`)

### 2-1. 갈래별로 나눠 제출하기
한 업무를 끝냈을 때 **서류 한 장에 전부 몰아 쓰지 않습니다.** 사장님이 갈래마다 따로 피드백할 수 있도록 **큰 갈래별로 서류를 나눕니다.**

- 갈래는 **사장님이 따로 판단할 수 있는 단위**로 나눕니다. 예: 화면 구성 / 색감 / 연출 / 기능 / 테스트·검증 / 질문
- 한 업무에 보통 **2~6장**. 너무 잘게 쪼개지 않습니다. (파일 단위 X, 판단 단위 O)
- 질문은 별도 서류(`종류: 질문`)로 분리해서 사장님이 답하기 쉽게 합니다.
- 서류 한 장 = 댓글 하나입니다.

### 2-2. 양식

```markdown
<!-- office:report -->
사원: gpt
번호: 2-2
갈래: 색감
종류: 작업보고
제목: 사무실 팔레트를 진한 나무 바닥 + 크림 벽으로 변경
PR: #6

## 한 일
- 바닥을 #7a583d 계열로, 벽을 #eae9db 계열로 변경
- 모든 가구에 짙은 갈색 외곽선 추가

## 사장님 확인 사항
- PR #6 스크린샷에서 바닥 밝기가 적당한지 봐 주세요.
```

| 항목 | 필수 | 값 |
|---|---|---|
| `사원` | ✅ | `claude` 또는 `gpt` |
| `번호` | ✅ | **문서 번호** `<Issue 번호>-<순번>` (예: `2-2`). 아래 §2-3 |
| `갈래` | ✅ | 이 서류가 다루는 큰 갈래 (짧은 이름, 예: `색감`) |
| `종류` | ✅ | `작업보고` / `중간보고` / `질문` / `검수결과` / `기획안` |
| `제목` | ✅ | 서류 제목 (홈페이지 서류 목록에 표시) |
| `PR` | ⬜ | 관련 PR 번호 (`#6`) |
| `답변` | ⬜ | 이 서류가 **피드백을 반영한 결과**라면, 원래 서류 번호. 여러 개면 쉼표 (`2-2, 2-3`) |
| 본문 | ✅ | 머리 항목 아래 빈 줄 다음부터 끝까지. 마크다운 자유 형식 |

- 머리 항목은 `키: 값` 형식이며 **빈 줄이 나오기 전까지**만 머리 항목으로 읽습니다.

### 2-3. 문서 번호 매기기
- 형식: `<Issue 번호>-<그 Issue 안의 순번>`. 순번은 1부터 시작합니다.
- 새 서류를 쓰기 전에 그 Issue의 기존 서류 중 가장 큰 순번을 확인하고 **+1**을 씁니다. 사원이 달라도 한 Issue 안에서는 순번을 공유합니다.
- 번호가 겹치면 피드 생성기는 **먼저 쓴 서류**를 인정하고 나중 서류는 경고와 함께 버립니다.
- 번호 앞부분은 **서류를 올린 Issue 번호와 같아야** 합니다. Issue #5에 올린 서류에 `6-1`을 쓰면 경고와 함께 버립니다.
- 피드백을 반영한 서류도 **새 번호**를 받습니다. 원래 서류와는 `답변:`으로 연결합니다.

## 3. 피드백과 결재 (사장님)

사장님은 서류를 읽고 **언제든 피드백·결재를 쌓아 둘 수 있습니다.** 이 댓글만으로는 사원이 깨어나지 않습니다. 사원은 다음 출근(§4) 때 쌓인 피드백을 한꺼번에 가져갑니다.

### 3-1. 명령

댓글 **첫 줄**이 아래 명령으로 시작해야 합니다. 한 댓글에 명령 하나만 씁니다.

| 명령 | 예시 | 뜻 |
|---|---|---|
| `/피드백 <번호> <내용>` | `/피드백 2-2 바닥이 너무 어두워요. 한 단계 밝게.` | 해당 서류에 수정 요청. 내용은 여러 줄 가능 (댓글 끝까지). **내용이 없으면 무시** |
| `/승인 [번호...] [아무 말]` | `/승인 2-1 2-3`, `/승인 수고했어요` | 해당 서류 승인. 번호 여러 개 가능 |
| `/반려 [번호] [사유]` | `/반려 2-4 테스트가 실패해요.` | 해당 서류 반려. **반려도 처리해야 할 피드백으로 취급**합니다. 사유는 생략 가능 |

**번호 읽는 법** (사장님이 평소 말투로 써도 결재가 빠지지 않게)
- `/승인`: 뒤에 오는 말 중 **번호 모양(`5-1`)만** 번호로 읽고, 나머지 말은 무시합니다. 번호가 하나도 없으면 **그 Issue의 가장 최근 서류**에 적용합니다.
  - `/승인` · `/승인 수고했어요` · 첫 줄 `/승인` + 다음 줄 아무 말 → 가장 최근 서류
  - `/승인 5-1 잘했어요` → 5-1
- `/반려`: 바로 뒤가 번호 모양이면 그 서류, 나머지는 사유입니다. 번호 모양이 아니면 **가장 최근 서류**에 적용하고 전체를 사유로 봅니다.
  - `/반려 5-2` → 5-2를 사유 없이 반려 · `/반려 다시 해 주세요` → 가장 최근 서류
- `/피드백`: 바로 뒤에 번호가 **반드시** 있어야 합니다. (어느 서류를 고칠지 모르면 처리할 수 없음)
- **번호를 잘못 쓴 것 같은 말**(숫자와 `-`로 시작하지만 번호 모양이 아닌 말, 예: `5-1번`, `5-`)은 엉뚱한 서류에 결재가 들어가지 않도록 이렇게 처리합니다.
  - `/승인`: 제대로 된 번호가 **하나도 없고** 잘못 쓴 번호가 있으면 **명령 전체를 무시**합니다. (가장 최근 서류로 넘어가지 않음) 제대로 된 번호가 있으면 잘못 쓴 말은 그냥 무시합니다.
  - `/반려`: **바로 뒤의 첫 말**이 잘못 쓴 번호면 명령 전체를 무시합니다. 사유 속의 `3-4번` 같은 말은 상관없습니다.
- 명령은 **그 서류가 있는 Issue에** 써야 합니다. 다른 Issue에서 `/피드백 6-2`처럼 쓰면 무시하고 경고를 남깁니다.
- `/승인`의 번호 중 일부가 없는 서류를 가리키면 그 번호만 무시하고 나머지는 적용합니다.
- 결재·피드백 댓글은 **사장님이 GitHub 웹에서 직접** 쓰거나 **홈페이지 결재 버튼**(§3-3)으로 써야 인정됩니다. (§6 신원 확인)

### 3-3. 홈페이지 결재 버튼

사장님은 댓글을 직접 쓰지 않고 **홈페이지 서류 창의 버튼**으로도 결재할 수 있습니다. 버튼은 위 명령 댓글을 사장님 계정으로 대신 써 주는 장치이므로, 해석 규칙(§3-1, §3-2)과 신원 확인(§6)은 그대로입니다.

| 버튼 | 사장님 입력 | 홈페이지가 쓰는 댓글 (해당 서류의 Issue에) |
|---|---|---|
| **[승인]** | 없음 | `/승인 <번호>` |
| **[반려]** | 사유 (선택) | `/반려 <번호> <사유>` |
| **[피드백]** | 내용 (필수, 여러 줄 가능) | `/피드백 <번호> <내용>` |

- **열쇠**: 버튼을 쓰려면 사장님이 자기 브라우저에 **세분화된 개인 액세스 토큰**(fine-grained PAT, `github_pat_`로 시작)을 한 번 등록합니다. 권한은 **이 저장소 하나, Issues 읽기·쓰기만** 줍니다. 만드는 법: [`docs/guides/ceo-setup.md` §6](../docs/guides/ceo-setup.md#6-결재-버튼-열쇠-등록-한-번만)
- 열쇠는 **그 브라우저에만** 저장되고 `api.github.com` 외에는 어디로도 보내지 않습니다. 저장소·Secrets·AI에는 절대 넣지 않습니다.
- 홈페이지는 열쇠를 등록할 때 `GET /user`로 **열쇠 주인이 저장소 주인(`moooncang`)인지 확인**하고, 아니면 등록을 거부합니다.
- 이 열쇠로 쓴 댓글은 앱 기록이 `null`로 남으므로 §6 판별표에서 **사장님**으로 인정됩니다. (피드 생성기 수정 불필요)
- 버튼을 누른 뒤 홈페이지에 반영되기까지 1~2분 걸립니다. 그동안 서류에 "결재 반영 중"을 표시합니다.
- **번호 없는 v1 서류**는 번호로 가리킬 수 없으므로, 그 Issue의 **가장 최근 서류일 때만** 번호 없는 명령(`/승인`, `/반려 사유`)으로 버튼을 제공합니다. 아니면 버튼 대신 안내 문구를 보여 줍니다.

### 3-2. 서류 상태 (피드 생성기가 계산)

| 상태 | 뜻 | 홈페이지 표시 |
|---|---|---|
| `pending` | 아직 사장님이 아무것도 안 남김 | 결재 대기 |
| `feedback` | 처리해야 할 `/피드백`·`/반려`가 남아 있음 | 피드백 있음 (붉은 메모) |
| `answered` | 사원이 남은 피드백을 모두 반영한 답변 서류를 냄 | 반영 완료 → 답변 서류로 링크 |
| `approved` | 사장님이 승인함 | 승인 도장 |

**계산 방법: 서류마다 아래 사건을 시간 순서대로 적용하고, 마지막 상태를 씁니다.** (시작 상태 `pending`)

| 사건 | 바뀌는 상태 | 미처리 피드백 목록 |
|---|---|---|
| 사장님 `/피드백` 또는 `/반려` | `feedback` | 이 피드백을 추가 |
| 같은 사원이 `답변:`에 이 번호를 넣은 서류 제출, 그리고 그 시점에 미처리 피드백이 1개 이상 | `answered` | 그 시점까지의 미처리 피드백을 모두 처리 완료로 표시 (`resolved_by` = 답변 서류 번호) |
| 위와 같지만 미처리 피드백이 0개 | 변화 없음 | 변화 없음 (경고만) |
| 사장님 `/승인` | `approved` | 남은 미처리 피드백을 모두 닫음 (사장님이 그대로 승인한 것으로 봄, `resolved_by` = `null`) |

- 답변 서류는 **피드백보다 나중에 쓴 것**만 그 피드백을 처리합니다. (시간 순서대로 적용하면 자동으로 지켜짐)
- 승인 뒤에 다시 `/피드백`이 오면 `feedback`으로 돌아갑니다.
- 다른 사원이 `답변:`에 이 번호를 넣어도 처리로 보지 않습니다. (피드백은 그 서류를 쓴 사원만 처리)
- 판정 기준표: 이 규칙들의 입력과 기대 결과 예시는 [`fixtures/`](fixtures/)에 있습니다. 피드 생성기는 이 예시를 모두 통과해야 합니다.
- `open_feedback`(§5) = 그 사원이 쓴 서류들의 미처리 피드백 개수 합계

## 4. 출근 (업무 시작)

사원은 **사장님이 출근 버튼을 눌렀을 때만** 깨어나 일합니다.

### 4-1. 출근 버튼

| 버튼 | 동작 |
|---|---|
| `[GPT 출근]` | GPT만 실행 |
| `[Claude 출근]` | Claude만 실행 |
| `[전원 출근]` | 기본 **순서대로**: GPT가 먼저 일하고 끝나면 Claude가 출근해서 검수. `동시` 옵션을 고르면 둘이 함께 시작 |

- 출근 버튼은 GitHub Actions의 수동 실행(`workflow_dispatch`)으로 만듭니다. GitHub에 로그인한 저장소 주인만 실행할 수 있어 외부인이 사원을 깨울 수 없습니다.
- **한 사원은 동시에 한 번만** 출근합니다. 이미 일하는 중인 사원의 출근 버튼을 또 누르면 앞 작업이 끝난 뒤 시작합니다. (Actions `concurrency` 그룹 = 사원 ID)

### 4-2. 출근한 사원이 하는 일 (순서)
1. `office:status` 출근 보고
2. **처리 대상 모으기**
   - 자기가 쓴 서류 중 상태가 `feedback`인 것 전부 (모든 열린 Issue 대상)
   - 자기 담당 라벨(`담당:<사원ID>`)이 붙은 열린 Issue 중 아직 서류를 안 낸 새 업무
   - Claude는 추가로: 검수를 기다리는 GPT의 열린 PR
   - ⚠️ 피드백은 **§6 신원 확인으로 사장님 댓글임이 확인된 것만** 가져옵니다. 공개 저장소라 외부인도 `/피드백`처럼 보이는 댓글을 달 수 있습니다. 가능하면 피드 생성기가 만든 목록(`feed.json`의 `status: feedback` 서류)을 그대로 씁니다.
3. 처리. 피드백은 **그 서류를 쓴 사원만** 처리합니다. 다른 사원 서류의 피드백은 건드리지 않습니다.
4. 결과를 갈래별 서류로 제출. 피드백 반영이면 `답변:`에 원래 번호
5. `office:status` 퇴근 보고 (`idle` 또는 `offline`)

### 4-3. 동시 작업 규칙 (꼬임 방지)
- **파일 담당표**를 지킵니다. ([`AGENTS.md` §2](../AGENTS.md)) 담당이 아닌 파일은 고치지 않고 Issue 댓글로 요청합니다.
- **머지 안 된 PR에 기대는 작업**은 하지 않습니다. 필요한 PR이 머지되지 않았으면 `blocked` 상태와 `질문` 서류로 알립니다.
- `[전원 출근]`은 기본이 **순서대로**입니다. 두 사원이 같은 파일을 만질 가능성이 없을 때만 `동시`를 씁니다.

## 5. 홈페이지용 피드 (`feed.json`)

피드 생성기(GitHub Actions)가 위 댓글들을 모아 만드는 파일입니다. 홈페이지는 이 파일만 읽습니다.
예시: [`samples/feed.sample.json`](samples/feed.sample.json)

```jsonc
{
  "version": 2,
  "generated_at": "2026-10-07T12:00:00Z",   // 생성 시각 (UTC, ISO 8601)
  "repo": "moooncang/game",
  "employees": {
    "gpt": {
      "name": "GPT",
      "state": "coding",                     // 상태 코드
      "message": "2-2 피드백 반영 중",
      "task": 2,                             // 현재 업무 Issue 번호 (없으면 null)
      "updated_at": "2026-10-07T11:58:00Z",
      "open_feedback": 1                     // 이 사원이 처리해야 할 미처리 피드백 수
    },
    "claude": { "...": "같은 구조" }
  },
  "tasks": [                                 // 업무 Issue 목록 (최근 순)
    {
      "number": 2,
      "title": "홈페이지 개편",
      "assignee": "gpt",                     // 담당 라벨에서 추출 (없으면 null)
      "state": "open",                       // open / closed
      "url": "https://github.com/moooncang/game/issues/2"
    }
  ],
  "reports": [                               // 서류 목록 (최근 순)
    {
      "id": 1234567890,                      // 댓글 ID
      "doc": "2-2",                          // 문서 번호
      "task": 2,
      "author": "gpt",
      "branch": "색감",                      // 갈래
      "kind": "작업보고",
      "title": "사무실 팔레트 변경",
      "pr": 6,                               // 없으면 null
      "answers": ["2-1"],                    // 이 서류가 반영한 원래 서류 번호들 (없으면 [])
      "body_md": "## 한 일\n- ...",
      "created_at": "2026-10-07T11:50:00Z",
      "status": "feedback",                  // pending / feedback / answered / approved
      "feedback": [                          // 사장님 피드백·결재 기록 (오래된 순)
        {
          "type": "feedback",                // feedback / approve / reject
          "body_md": "바닥이 너무 어두워요.",
          "at": "2026-10-07T11:55:00Z",
          "closed": false,                   // 닫힘 여부: 답변 서류로 처리됐거나 승인으로 닫히면 true. approve 기록은 항상 true
          "resolved_by": null,               // 처리한 답변 서류 번호 (승인으로 닫혔거나 열려 있으면 null)
          "url": "https://github.com/moooncang/game/issues/2#issuecomment-..."
        }
      ],
      "answered_by": null,                   // 이 서류를 반영한 최신 답변 서류 번호
      "url": "https://github.com/moooncang/game/issues/2#issuecomment-1234567890"
    }
  ]
}
```

### 해석 규칙 (피드 생성기 구현 시)
1. 사원 상태 = 모든 Issue를 통틀어 그 사원의 **가장 최근** `office:status` 댓글. 한 번도 없으면 `offline`.
2. 상태 댓글이 **12시간 넘게** 갱신되지 않으면 `offline`으로 간주합니다. (퇴근 보고를 빠뜨린 경우 대비)
3. **작성자 판별은 반드시 §6 "신원 확인" 규칙을 따릅니다.** 댓글 본문의 `사원:` 값만 믿으면 안 됩니다.
4. 양식이 깨진 댓글(필수 항목 누락, 없는 문서 번호를 가리키는 명령)은 버리고, 생성기 로그에 경고만 남깁니다.
5. v1 서류(`번호` 없음)는 `doc: null`로 두고, 번호 없는 `/승인`·`/반려`만 적용합니다.

## 6. 신원 확인 (누가 쓴 댓글인가)

두 AI 사원은 모두 사장님 계정(`moooncang`)의 권한을 빌려 GitHub에 글을 씁니다. 그래서 **계정 이름만으로는 사장님과 AI를 구분할 수 없습니다.**
대신 GitHub는 앱을 통해 작성된 댓글마다 그 앱을 `performed_via_github_app` 필드에 **자동으로 기록**합니다. 이 값은 GitHub 서버가 토큰 종류를 보고 정하므로 AI가 바꿀 수 없습니다.

### 판별표

| `user.login` | `performed_via_github_app.slug` | 판별 결과 |
|---|---|---|
| `moooncang` | `claude` | 사원 **claude** |
| `moooncang` | `chatgpt-codex-connector` | 사원 **gpt** |
| `moooncang` | 없음 (`null`) | **사장님** |
| 출근 워크플로가 쓰는 봇 계정 (예: `github-actions[bot]`, `claude[bot]`) | 해당 앱 | **사원** (아래 참고) |
| 그 밖의 모든 경우 | | 무시 (외부인, 다른 앱 등) |

- 위 세 줄은 2026-10-07에 실제 댓글로 확인한 값입니다. (Issue #2의 GPT 댓글 = `chatgpt-codex-connector`, Claude가 만든 Issue = `claude`, 사장님이 웹에서 쓴 댓글 = `null`)
- **출근 워크플로(§4)에서 사원이 실행되면 다른 봇 계정으로 댓글이 남을 수 있습니다.** 출근 기능을 구현할 때 실제로 남는 `user.login`과 앱 slug를 확인해서 이 표에 추가합니다.
  - 봇 계정은 저장소 워크플로 안에서만 글을 쓸 수 있고, 워크플로는 사장님이 머지한 코드만 실행되므로 사원 댓글로 인정합니다.
  - 두 사원이 같은 봇 계정(예: `github-actions[bot]`)을 쓰면 그 계정 안에서는 본문의 `사원:` 값으로 구분합니다.
- 이 표는 피드 생성기의 **설정 값**으로 둡니다. 저장소 주인 이름, 앱 slug가 바뀌면 설정만 고칩니다.

### 적용 규칙
1. **상태·서류 댓글**(`office:status`, `office:report`)은 판별 결과가 **사원**인 댓글만 인정합니다.
   - 본문의 `사원:` 값이 판별 결과와 다르면 버리고 경고를 남깁니다. (예: `claude` 앱으로 쓴 댓글에 `사원: gpt`)
2. **피드백·결재 댓글**(`/피드백`, `/승인`, `/반려`)은 판별 결과가 **사장님**인 댓글만 인정합니다.
   - AI가 실수로든 고의로든 이 명령을 써도 앱 기록이 남으므로 처리되지 않습니다.
3. 판별 결과가 **무시**인 댓글은 전부 건너뜁니다. 공개 저장소라 누구나 댓글을 달 수 있기 때문입니다.

### 이 규칙이 깨지는 경우 (금지 사항)
- AI 사원에게 사장님의 **개인 액세스 토큰(PAT)을 주면 안 됩니다.** PAT로 쓴 댓글은 앱 기록이 `null`로 남아 사장님 결재와 구분할 수 없습니다.
  - 예외는 **사장님 본인의 브라우저에 등록하는 결재 버튼용 열쇠**(§3-3) 하나뿐입니다. 이 열쇠도 저장소 파일, Actions Secrets, AI 대화에는 넣지 않습니다.
- AI 사원은 각자의 공식 GitHub 연동(Claude GitHub 앱, ChatGPT Codex Connector) 또는 출근 워크플로로만 GitHub에 접근합니다.
- 사장님이 GitHub 모바일 앱 등 웹 외의 경로로 결재할 계획이라면, 그 경로의 댓글이 `null`로 기록되는지 먼저 한 번 시험해 보세요.
